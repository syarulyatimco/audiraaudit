# AUDIRA — PROJECT CONTEXT & DEVELOPMENT RULES

## 1. PROJECT IDENTITY

Project Name: AUDIRA

Product Type: AI-Powered Audit Management SaaS Platform

Primary Market: Malaysia

Target Customers:
- Small and medium-sized audit firms.
- Chartered Accountants.
- External auditors.
- Audit managers and partners.

AUDIRA is a professional audit management platform designed to automate and manage the complete external financial statement audit lifecycle.

AUDIRA is NOT just an accounting system, document management system or AI chatbot.

It is an integrated audit ecosystem with autonomous AI agents that can perform assigned audit tasks, communicate with clients, analyse documents, prepare audit working papers and support audit completion.

## 2. PRODUCT VISION

The objective is to allow an audit firm to manage an entire audit engagement through one platform.

The auditor should be able to:
1. Create an audit engagement.
2. Understand the client.
3. Import the trial balance.
4. Map accounts to financial statement line items.
5. Calculate materiality.
6. Assess audit risks.
7. Generate audit programmes.
8. Determine sampling methodology and select samples.
9. Request documents from clients.
10. Perform audit testing.
11. Analyse audit evidence.
12. Record audit findings.
13. Prepare working papers.
14. Complete audit procedures.
15. Review and finalise the audit.

AI agents should execute repetitive and analytical tasks while auditors retain responsibility for professional judgement and audit opinions.

## 4. MALAYSIAN AUDIT ENVIRONMENT

Design the system primarily for Malaysian external audit practices.

Support configurable reporting and audit libraries:

- MFRS.
- MPERS.
- MPSAS.
- ISA and applicable Malaysian approved auditing standards.
- JMB / MC reporting requirements.
- SKM-related reporting requirements.
- Companies Act 2016.
- Other relevant reporting frameworks.

Do not fabricate standards, paragraphs or regulatory requirements.

Standards must be maintained in a version-controlled library using authorised source materials.

Every technical reference generated by AI must identify its source and paragraph reference where available.

## 6. MATERIALITY REQUIREMENTS

The system must support:

- Overall Materiality.
- Performance Materiality.
- Specific Materiality.
- Clearly Trivial Threshold.

AI may recommend benchmarks and percentages but must not approve materiality.

Materiality must be linked to:
- Trial balance.
- Financial statements.
- FSLI.
- Risk assessment.
- Audit strategy.
- Sampling.
- Misstatement evaluation.

Store calculation assumptions, rationale, preparer, reviewer and approval history.

Never assume that a fixed percentage is universally required by ISA.

## 7. SAMPLING REQUIREMENTS

Sampling is a core audit module.

Support:
- Statistical sampling.
- Non-statistical sampling.
- Random sampling.
- Systematic sampling.
- Haphazard selection.
- Risk-based judgemental selection.
- Stratified sampling.
- Monetary Unit Sampling.

The system must:
- Validate population completeness.
- Reconcile population to relevant accounting records.
- Identify individually significant items.
- Calculate sample sizes using documented methodologies.
- Select samples reproducibly.
- Retain random seed and selection logs where applicable.
- Record sample testing results.
- Evaluate identified misstatements.
- Project misstatements where appropriate.
- Assess the need for additional procedures.

Do not use arbitrary sample sizes or represent judgemental selection as statistical sampling.

Auditor approval is mandatory before finalising the sampling plan.

Security is non-negotiable.

- Role-based access control.
- Engagement-level permissions.
- Secure authentication.
- Encryption.
- Secure document storage.
- Audit activity logs.

## 15. DEVELOPMENT APPROACH

Work incrementally.

Do not attempt to develop the entire application in one operation.

For every development phase:

1. Inspect existing implementation.
2. Identify required changes.
3. Explain the implementation plan.
4. Implement backend.
5. Implement frontend.
6. Implement database changes.
7. Add validation and permissions.
8. Write tests.
9. Run tests.
10. Fix errors.
11. Update documentation.
12. Report completed work.

Do not move to the next major phase while critical errors remain unresolved.

## 16. FINAL PRODUCT STANDARD

AUDIRA must be a functional, secure, scalable and commercially viable SaaS platform.

The final product must support real audit engagements, real document uploads, real database persistence, functional AI agents, working approval workflows and reliable audit trails.

Always prioritise audit accuracy, confidentiality, professional judgement and system reliability over development speed.

All roadmap phases (0–10) are delivered; remaining work is the go-live checklist and open business decisions in docs/ROADMAP.md and docs/SECURITY.md. Full tracker: docs/ROADMAP.md.
- Stack in use is exactly §10: Laravel 12, Blade, Alpine.js 3, Tailwind CSS 3, PostgreSQL 16, Redis. Added packages: pragmarx/google2fa, bacon/bacon-qr-code.
- Tenancy rules every new module must follow: tenant tables carry `firm_id`, use the `BelongsToFirm` trait, and are added to an RLS migration (docs/SECURITY.md, ADR-002).
- Every human-approval gate in §9 goes through `ApprovalService` and an `Approvable` model (ADR-004). Working-paper sign-offs are bound to content hashes (ADR-009); lead-schedule papers include their FSLI figures.
- Money is integer sen; TB balances are signed (debit positive). Imported TB lines and posted adjustments are immutable (ADR-013, ADR-015). Mapping suggestions are never applied without a person accepting them (ADR-014).
- The Audit Library ships with framework structure only. Standard text must be loaded by the Superadmin from authorised, licensed sources; never generate it (§4, ADR-010).
- When writing files with scripts, never let regex backslashes be interpreted as escape sequences (see Phase 3 changelog fix).
- AI rules (ADR-017–021, docs/AI_AGENTS.md §7): agents live in `app/Ai`, are registered in `config/ai.php` with a tool allow-list, and name a model *tier*, never a model. Tools are scoped through `ToolContext`, declare a permission and an input schema, and only read or write drafts. Every task has an output schema and a `guard()`; anything removed or doubted makes the run `needs_review`. Agents never apply changes themselves: a person accepts through the normal service. AI is off until a firm admin opts in.
- Engagement-scoped approvals: implement `approvalEngagement()` on the Approvable and add the type to `audira.approval_engagement_roles` (ADR-023). Materiality in force: `Engagement::currentMateriality()` (ADR-022). Planning papers A1/C1/D1 have sign-off gates in `PlanningPapers::gates()` (ADR-025).
- Agents may cite only library paragraphs returned by `library_search` in the same run; use `Agent::verifiedCitations()` (ADR-026).
- Sampling: never hard-code a sample size or methodology factor; use `SamplingMath` and store the calculation (ADR-027). Approved plans and selections are frozen by triggers (ADR-028).
- Client portal users never reach firm routes; portal code must re-check `client_id` ownership. Outbound client messages are sent only by people (ADR-029, ADR-030).
- Findings and adjustments: misstatements are stored as recorded − audited per FSLI; material adjustments need a partner approval bound to the lines hash (ADR-031, ADR-032). AI-drafted test results must quote evidence verbatim (ADR-033).
- Completion and reporting: conclusions → EQR → completion → opinion → sign-off, each a gated approval (ADR-034). The opinion is the partner's and report wording is the firm's template; `audit_opinion` and `report_signoff` require re-authentication; no agent may touch the opinion (ADR-035).
- Billing is gateway-agnostic with no tax assumed (ADR-037); monitoring is rules first (ADR-038); support access is firm-granted, time-boxed and metadata-only (ADR-039).
- Eloquent collections: `->except()` and `->diff()` work on model primary keys, not array keys — use `reject(fn ($v, $k) => …)` for keyed collections (Phase 8/10 fixes).
- Browser forms send strings: never compare request values with integers using strict `in_array` without casting (Phase 5 fix).
- Tests run on PostgreSQL as a non-superuser role: `vendor/bin/phpunit`. AI tests must fake the provider (`AiTestCase`); never let tests reach a real endpoint.
